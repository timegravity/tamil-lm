# Harness notes (eval/suite.py and the comparison driver)

## 2026-09-12: batched greedy generation, eager attention, harness versions

- Generation tasks (translation, IndicQA, GSM8K, XL-Sum) decode greedily in left-padded, length-sorted batches (SUITE_GEN_BATCH, 32 for models under 5B, 16 above) with a 12,000 prompt-token budget per batch that bounds the KV cache. Log-likelihood tasks are unchanged.
- Finding: with the default SDPA attention, left padding shifted Gemma-3-1B's scores (IN22 ta-en chrF++ 39.07 single-item to 36.45 batched; FLORES ta-en 40.39 to 38.45), with garbled first tokens on the longer prompts. Our model was unaffected. With eager attention the batched numbers match single-item decoding within noise on both models on every task (eval/results/batch_check.md). Every batched run therefore uses eager attention (SUITE_ATTN=eager), for every model.
- GSM8K on the 40-item dev sample moves by 3 items under the eager kernel itself (single-item eager equals batched eager), so its batching comparison uses the single-item eager reference; both references are printed.
- Every result row carries "harness" (a content hash of suite.py, the prompt files and the loaders, plus the generation mode and attention implementation, for example 564e6d1b50:batched-eager), "gen_mode" and "gen_batch". A table refuses to render when its rows would mix harness versions; the version is named in each table title.
- Throughput: single-item Gemma-3-1B raw test pass, FLORES 1,012 items in 48 minutes (2.8 s per item); batched eager on the 300-item dev sample, FLORES in 33 to 127 s (0.1 to 0.4 s per item).
- The single-item Gemma-3-1B raw test pass (sdpa) is kept as eval/results/cmp_Gemma-3-1B-it_single_test.json and compared with the batched eager pass on the full split; Gemma-3-1B stays in the tables only if that comparison passes.
- Dev rows under the new harness are written as cmp_<model>_v2_dev.json; the dev table switches from the legacy single-item files to the v2 files only once every model has one (no mixed versions).
- GSM8K correction (same day): single-item eager gave 0.050 (ours) and 0.225 (Gemma-3-1B) against batched eager 0.125 and 0.325 on the 40 dev items, so the shift is batching itself on long chain-of-thought generations, not the kernel. GSM8K therefore decodes one item at a time in every mode (160 test items, cheap); translation and IndicQA stay batched. The batch check re-runs on the final code and records the verified harness version; the driver refuses to run when the verified version differs from its own.
- 2026-09-13 (ruling): batched-versus-single check v2: 100 dev items per generation task (FLORES both ways, IN22 both ways, IndicQA, GSM8K), the single-item half only for those tasks; log-likelihood tasks (MILU, MMLU, bpc, probe) are not affected by generation batching and are compared batched-only against the single-item Gemma-3-1B full-split reference. Thresholds widened by sqrt(3): chrF++ 3.5, F1 0.035, contains 0.05, accuracy 0.05 (GSM8K dev has 40 items either way). Models already checked under v1 (Llama-3.2-1B; ours and Gemma-3-1B in batch_check.md) keep their result; the spec used is recorded per model in comparison_bare_state.json and in the table footnote. The row-level harness hash (scoring code, prompts, loaders, attention) is unchanged by this: the check decides a model's decoding mode, which the rows already record as gen_mode.
- Observed: IndicQA batched is slower than single-item for high-fertility tokenizers (Llama: 6,000-token contexts, batches of two under the 12,000-token budget, 1,316 s batched against 457 s single on 255 items); translation gains 6x to 26x.

## 2026-09-13: start-token rule bos-v1, degenerate-output check, carry-forward by token identity (harness 94492e3d4d)

- Finding: Gemma 4's tokenizer adds no start token to plain text, and its raw-mode generations degenerated ("English:" repeated) with bpc near 5 (Tamil) and 8 (Tanglish). The harness had relied on each tokenizer's own special tokens for raw generation and bpc, and used no special tokens at all for log-likelihood prompts, so on MILU, MMLU, Belebele and the other choice tasks in raw mode no model had a start token.
- Rule bos-v1 (ruling 2026-09-13): raw prompts and bpc texts begin with the tokenizer's own defined start token (bos_token_id) whenever it defines one, and carry no other special tokens (eval/suite.py raw_ids, prompt_ids; eval/run_probe.py uses the same function). Chat-templated prompts are unchanged. Batched generation now builds the left-padded tensors from the same per-item ids as single-item decoding. run_probe.py joined the hashed harness files, and probe files carry the harness version.
- Which inputs changed (eval/harness_carry.py, eval/results/harness_carry_bos_v1.json, every item of every task compared token by token): our model, Qwen3.5-2B and Qwen3-1.7B-tamil define no start token, so nothing changed for them; Gemma-3-1B, Llama-3.2-1B, Llama-3.2-3B, Sarvam-1 and BharatGPT-3B already had the token added on generation and bpc, so only their raw MILU and MMLU inputs changed (all 25,488 and 1,600 scored continuations). Chat-mode inputs and the batched-versus-single check inputs were identical for all eight finished models.
- As ruled, every raw phase of the eight finished models re-runs (raw dev, raw test, probe; translation captures come with the raw test). The earlier files are kept in eval/results/pre_bos/ for eval/bos_before_after.py. Carried to the new version because their inputs are identical: chat-mode test rows, each model's check result and the batch verification in batch_check.json; carried rows keep the old version in harness_carried_from with the check named in carry_check. Models with unchanged raw inputs must reproduce their raw numbers exactly, which also tests the rewritten batching code.
- Degenerate-output check (ruling 2026-09-13; three artefacts had been caught by eye): a generation task is flagged when at least half of its generations repeat the prompt's last line or loop on one line, when a translation task scores chrF++ below 2 with at least half of its generations non-empty, or when Tamil bpc exceeds 4.8 or Tanglish bpc 6.0. The run writes the rows with a "degenerate" field and exits with an error; tables show "degenerate" instead of a score and list the reason. Calibration on every existing capture: only the Gemma-4-E4B runs trip the repetition rule (83 to 99 percent; next highest Qwen3.5-2B base raw 40 percent); the bpc limits sit above the highest real values (4.45 and 4.41). A flag can be cleared only by an entry with its reason in eval/degenerate_reviewed.json, footnoted in the tables: Qwen3-1.7B-tamil in chat mode answers Tamil-to-English requests in Tamil (chrF++ 1.97 and 1.78), a model failure, kept as measured.
- Also corrected: Sarvam-1's tokenizer ships a Llama 2 style [INST] chat template and table (b) used it; the card note said it had none.

## 2026-09-13 22:00 UTC: harness v3 after a three-part audit (measurement code, runs and results, card claims)

Findings verified before changing anything, and the change made for each:
- Generation caps truncated high-fertility tokenizers. Tamil references longer than 160 tokens: Llama-3.2 (and BharatGPT) 725 of 1,012 FLORES and 603 of 820 IN22 en-ta; Qwen3-1.7B-tamil 505 and 468; ours 0 and 2; Gemma 0 and 7. Captures showed 358 Llama-3.2-3B translations cut mid-character (U+FFFD). IndicQA at 48 tokens could not hold the shortest gold answer for 46 items in Llama tokens; the probe's kural quote at 64 tokens could not hold any kural in Llama tokens. Hosted models were cut too (Gemini 3.5 Flash-Lite: 177 translations, 170 IndicQA answers and 72 of 160 GSM8K answers at the cap; GPT-5.4 nano: 298 IndicQA answers). v3: each tokenizer's cap is the larger of the task's base cap (translation 160, IndicQA 48, XL-Sum 120, kural quote 64) and 1.25 times the 99th-percentile reference length in its own tokens; GSM8K 512 for every model; generation stops once the scored line is complete (a completed line that is neither empty nor a preamble), so the first-line and extracted scores are both decided and longer caps cost time only where needed. The cap is recorded per row (gen_cap).
- GSM8K compared answers as strings: 46 numerically correct answers ("42.00" against "42") were marked wrong across the finished runs. v3 compares numbers.
- bpc: with a start token every character was scored; without one (ours, Qwen3.5, Qwen3-1.7B-tamil) the first text token was neither scored nor counted (ours counted 98.0 percent of Tamil and 96.4 percent of Tanglish characters). v3 uses the start token, or the end-of-sequence token when none exists, as context and divides by every character.
- Chat-mode letter scoring put " A" (with a leading space) after the template's assistant header; models then preferred one letter (Qwen3.5-2B chat picked C in 4,163 of 4,822 wrong MILU answers; chat MMLU 0.25 against raw 0.49). v3 scores "A" without the space after a template.
- Llama 3.2 style templates write today's date into every prompt; v3 passes a fixed date (13 Sep 2026, the date of every chat run so far).
- The offload load path (Sarvam-30B) and the probe ignored SUITE_ATTN while rows recorded "-eager"; v3 applies it everywhere.
- Batches were sorted by characters and budgeted by tokens (ours: 50 of 59 IndicQA batches over the budget); the driver set 8,000 tokens while these notes said 12,000. v3 sorts by token length and fixes the budget at 8,000 inside the suite.
- The version hash did not cover the split files or the probe set; it now does, rows record prompt_mode (raw or chat), rules (v3) and gen_cap, and the probe records the version of the code that ran.
- Degenerate check: a within-line loop rule and a two-line cycle rule were added; a review entry now clears a flag at render time too.
- The probe column labelled "letter log-likelihood accuracy" was the mean of four item types, two of them generation; it now shows the letter scorer on the two choice types.
- The capture wrapper wrote single-item generations twice (harmless; fixed).
- Checked and real, not a bug: Qwen3.5-2B Tamil bpc 4.27 under both eager and SDPA attention on 40 texts (English 0.9); its tokenizer spends 0.73 tokens per Tamil character.
- Not changed, noted: IndicQA dev and test share passages (644 of 1,022 test questions use a dev passage), IndicQA contexts are cut at 3,000 characters (the gold answer falls outside for 21 items, uniform across models), table (b) bpc is the same measurement as table (a), and IndicQA contexts overlap our pretraining text (Tamil Wikipedia; 1,022 of 1,022).
- Consequence: every local phase of every model re-runs under v3 (the batch verification and each model's batched-versus-single check too). The start-token before/after report stays valid: raw MILU, MMLU and Belebele inputs change only by the start token between the pre_bos files and v3.

## Card tables: transposed layout and best-score bolding (2026-09-14)

- Tables (a), (b), (d) and (e) are rendered with metrics as rows (name, direction and tie margin in the first column) and models as columns (name and parameter count), with a "model group" row; eval/table_rank.py makes every bolding decision from the result files and eval/table_bold_check.py re-derives the bold cells from the result JSON and compares them with the rendered markdown.
- Bold marks the best score by the metric's direction (higher for chrF++, accuracy, F1 and contains-answer rate; lower for bpc and tokens per Tamil word) and every score within the row's tie margin of it.
- Tie margins: chrF++ 1.0 point (the card's existing tie margin; per-sentence generations are not stored for every sentence of every model, so no sentence bootstrap is possible for all rows). Accuracy and contains-answer rate: 1.96 * sqrt(2 p (1 - p) / n), the 95% half-width of the difference of two independent proportions at the row's mean p and the split size n. IndicQA F1: the same formula; F1 lies in [0, 1], so its per-item variance is at most p (1 - p) and the margin is an upper bound (per-item F1 is not stored for every item). Bits per character: 0.02 bits, a stated fixed margin (bpc is a deterministic log-likelihood over a fixed text set and per-text values are not stored, so no resampling margin can be computed). Tokens per Tamil word: exact comparison at two decimals (deterministic). Literature probe accuracies use the proportion formula with n 190 per item type (380 for the letter scorer over the two choice types).
- Closed set: the comparison was closed on 2026-09-15 (eval/results/comparison_final.json). Models not run are listed once under table (a) and never appear as columns, so bolding carries no provisional caveat. Cells the degenerate-output check refused read "degenerate" and are never bolded.
